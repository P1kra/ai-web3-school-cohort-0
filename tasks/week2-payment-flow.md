# Week 2｜Minimal Payment and Commerce Flow Breakdown

## Agent 支付流程：从请求到结算

### 整体流程

```
┌──────────┐     ┌──────────────┐     ┌────────────┐     ┌──────────┐
│  AI Agent │────▶│ Payment Layer │────▶│ Blockchain │────▶│ Merchant │
│  (消费者)  │     │  (中间件)     │     │  (结算层)   │     │  (服务商)  │
└──────────┘     └──────────────┘     └────────────┘     └──────────┘
```

### 1. 请求阶段：Agent 发起支付意图

Agent 需要调用外部服务时，产生一个支付意图：
- **触发条件**：API 返回 402 Payment Required
- **意图内容**：金额、接收方、目的（"购买 1000 次 GPT-4 API 调用"）
- **人类可见**：意图以人类可读形式展示，包含金额、接收方、用途说明

### 2. 策略检查阶段：护栏机制

支付中间件在放行前检查：
1. **预算上限**：本周期剩余额度是否足够
2. **白名单**：接收方地址是否在允许列表
3. **频率限制**：过去 N 分钟内同类支付是否超出阈值
4. **金额阈值**：单笔是否超过需要人工审批的上限

低于阈值的 → 自动放行。超过阈值的 → 推送人类审批。

### 3. 执行阶段：链上结算

- **小额高频**：走 Layer 2（Base / Arbitrum），低 gas 费
- **大额低频**：走主网或直接提醒人类手动操作
- **支付通道**：x402 协议 → USDC 转账 → 链上确认

### 4. 验证阶段：人类可审计

- 每笔支付生成可读的收据（金额、时间、用途、tx hash）
- 定期汇总报告（日报/周报）
- 异常告警：金额异常、频率异常、新地址首次支付

### 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 结算网络 | Base L2 | 低 gas，生态成熟，USDC 流动性好 |
| 支付代币 | USDC | 稳定，避免价格波动影响预算管理 |
| 协议标准 | x402 | 开放协议，HTTP-native，不绑定特定钱包 |
| 签名方案 | Smart Account + Session Key | 可编程权限，可撤销，gas 抽象 |

### 最小可行流程（MVP）

1. Agent 收到 402 → 解析金额和接收方
2. 检查策略引擎 → 通过
3. 通过 Smart Account 发送 USDC
4. 等待链上确认 → 拿到 tx hash
5. 用 tx hash 换取 API 访问权限
6. 记录收据到审计日志
